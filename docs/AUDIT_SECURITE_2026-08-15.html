Reste à faire, par ordre de risque :

2. P0 DMARC neutralisé par un doublon

Le domaine n'a, de fait, aucune politique DMARC. Critique

Deux enregistrements TXT DMARC coexistent sur _dmarc.neogtb.fr :

$ dig +short _dmarc.neogtb.fr TXT
"v=DMARC1; p=quarantine; pct=100; sp=quarantine; aspf=s"
"v=DMARC1; p=none; rua=mailto:rua@dmarc.brevo.com"

La RFC 7489 §6.6.3 est sans ambiguïté : si la requête renvoie plus d'un enregistrement commençant par v=DMARC1, le récepteur doit considérer que le domaine n'a pas de politique DMARC du tout. Il n'y a ni fusion, ni « le premier gagne ».

Conséquence concrète : la politique p=quarantine que vous croyez appliquée n'est appliquée nulle part. Un tiers peut usurper @neogtb.fr en expédition sans que la moindre règle DMARC ne s'y oppose. Le premier enregistrement n'a par ailleurs pas de rua= : même s'il était seul, aucun rapport agrégé ne remonterait.

Enjeu de conformité. Le site expédie des courriels d'exercice des droits RGPD (app/Mail/GdprResponseMail.php, OverdueGdprNotificationMail.php) ainsi que les confirmations de newsletter en double opt-in. L'article 12.3 du RGPD impose une réponse sous un mois : une non-délivrance liée à l'authentification du domaine est un manquement opposable, pas un simple incident technique.

Correctif

Le second enregistrement est un résidu de l'intégration Brevo — SECURITY_NOTES.md demande d'ailleurs la révocation de la clé Brevo, et plus aucune ligne de code du dépôt ne référence Brevo. Chez le registrar :

# 1. SUPPRIMER l'enregistrement TXT résiduel sur _dmarc
#    "v=DMARC1; p=none; rua=mailto:rua@dmarc.brevo.com"

# 2. REMPLACER l'enregistrement restant par une version avec collecte de rapports
_dmarc.neogtb.fr.  IN  TXT  "v=DMARC1; p=quarantine; sp=quarantine; adkim=s; aspf=s; pct=100; rua=mailto:hello@neogtb.fr"

# 3. Vérifier qu'il n'en reste qu'UN SEUL (doit afficher une seule ligne)
dig +short _dmarc.neogtb.fr TXT

Ne pas passer à p=reject tout de suite, contrairement à ce que proposait la v1. Tant qu'aucun rua n'a collecté de rapports, personne ne sait quels expéditeurs légitimes existent (OVH, un éventuel outil marketing, les envois applicatifs). Passer directement en reject ferait silencieusement disparaître des courriels RGPD. Séquence : quarantine + rua → lecture des rapports pendant 2 à 4 semaines → reject.

À traiter dans la foulée

  • Le TXT brevo-code:e74d01d1317159e12d6125d9e8bbf721 est une vérification de propriété Brevo devenue sans objet — à supprimer avec le reste.
  • Le TXT "1|www.neogtb.fr" n'a pas de format connu documenté : identifier son émetteur avant de le retirer.
  • Aucun DKIM n'a été trouvé sur les sélecteurs usuels (mail, ovhmo1, brevo). Le sélecteur réel dépend de l'offre OVH : à récupérer depuis l'espace client, sans quoi le adkim=s ci-dessus n'a rien à valider.

3. P1 Le back-office renvoie une erreur 500

La page de connexion Filament est hors service en production. Élevé 
$ curl -s -o /dev/null -w "%{http_code}" https://admin.neogtb.fr/admin/login
500

La réponse est la page d'erreur générique de Symfony, pas la page d'erreur applicative Laravel : l'exception survient donc très tôt dans le cycle de requête, avant que le rendu applicatif ne prenne la main. Bonne nouvelle au passage : aucune trace d'exécution n'est exposée, ce qui confirme APP_DEBUG=false.

Piste principale. Le profil de panne correspond à l'historique connu du projet : session, cache et file d'attente partagent la même base SQLite en journal_mode=delete, ce qui produit des database is locked récurrents. Une session illisible fait échouer la requête avant le rendu — exactement ce que l'on observe. À confirmer sur le VPS :

# Sur le VPS — dernière exception enregistrée
ssh ubuntu@51.210.11.125
sudo tail -n 80 /var/www/neogtb-laravel-new/admin/storage/logs/laravel.log
sudo tail -n 40 /var/log/nginx/admin.neogtb.fr.error.log

# Si le diagnostic confirme les verrous SQLite :
#   .env → SESSION_DRIVER=file, CACHE_STORE=file, puis WAL sur la base applicative
sudo -u www-data php artisan config:clear

Cette panne était invisible pour la v1 parce qu'un scan d'en-têtes lit un code HTTP sans le qualifier : elle a même transformé l'anomalie en point positif, en présentant la réponse du sous-domaine comme un « accès restreint (403) » alors que la racine répond 200 et la page de connexion 500.

4. P1 Le site public entier est servi sur admin.neogtb.fr

Duplicat complet et indexable du site sur le sous-domaine d'administration. Élevé 
$ for u in / /gtb /blog; do curl -s -o /dev/null -w "$u → %{http_code}\n" https://admin.neogtb.fr$u; done
/ → 200
/gtb → 200
/blog → 200

$ curl -s https://admin.neogtb.fr/gtb | grep -o '<link rel="canonical"[^>]*>'
<link rel="canonical" href="https://admin.neogtb.fr/gtb" />

$ curl -s https://admin.neogtb.fr/ | grep -o 'name="robots"[^/]*'
name="robots" content="index, follow, max-image-preview:large, …"

Les deux vhosts partagent la même racine applicative, mais seul le bloc public porte la redirection canonique if ($host != "neogtb.fr"). Résultat : chaque page du site existe en double sur admin.neogtb.fr, avec un canonical auto-référent vers le sous-domaine — c'est-à-dire que les pages dupliquées se déclarent elles-mêmes comme version de référence. Le robots.txt servi là est celui du site public : il autorise Allow: /.

Deux dommages distincts :

  • SEO — contenu dupliqué à l'échelle du site entier, sur un sous-domaine qui s'auto-désigne comme canonique. Sur un site dont la stratégie repose sur le référencement et la citation par les moteurs génératifs, c'est le poste le plus coûteux de cet audit.
  • Sécurité — l'existence et l'adresse du back-office deviennent découvrables par simple exploration de l'index, et toute la surface applicative publique est exposée une seconde fois, sur un hôte dont ce n'est pas la fonction.

Et ce n'est pas le seul duplicata. https://www.neogtb.fr répond lui aussi 200, avec un canonical auto-référent https://www.neogtb.fr/gtb — alors que la configuration versionnée porte bien une redirection canonique if ($host != "neogtb.fr") sur le bloc public. Elle n'est donc pas appliquée en production : nouvelle preuve de la dérive décrite en §5.2, cette fois dans le sens où la production est moins stricte que le dépôt. Le site existe donc en trois exemplaires indexables : apex, www et admin.

$ curl -s -o /dev/null -w "%{http_code}" https://www.neogtb.fr/
200
$ curl -s https://www.neogtb.fr/gtb | grep -o '<link rel="canonical"[^>]*>'
<link rel="canonical" href="https://www.neogtb.fr/gtb" />

Un middleware ForceCanonicalDomain existe pourtant dans le dépôt (app/Http/Middleware/ForceCanonicalDomain.php) — mais il n'est branché nulle part : aucune référence dans bootstrap/app.php, ni dans les routes. Et il ne pourrait pas l'être en l'état : appliqué globalement, il redirigerait admin.neogtb.fr vers neogtb.fr et rendrait le back-office inaccessible. Le correctif appartient donc à nginx, où la distinction entre les deux vhosts existe déjà.

👉 Correctif écrit et versionné : voir §8.

5. P2 En-têtes absents sur les assets & dérive de la configuration

5.1 — Aucun en-tête de sécurité sur /build/

$ curl -sI https://neogtb.fr/build/assets/app-DoCLPraW.css
HTTP/2 200
content-type: text/css
cache-control: max-age=31536000
cache-control: public, immutable
# ni x-content-type-options, ni referrer-policy, ni cross-origin-resource-policy

La cause est une règle nginx que la v1 mentionnait en note de bas de page sans faire le lien avec sa propre mesure : dès qu'un add_header apparaît dans un bloc location, tous les add_header du bloc server parent sont ignorés pour ce bloc. Le add_header Cache-Control des assets neutralise donc l'intégralité des en-têtes de sécurité du site sur les fichiers CSS et JavaScript.

L'absence de nosniff sur des ressources statiques n'est pas cosmétique : c'est précisément le scénario où un navigateur peut réinterpréter le type d'une réponse. À noter aussi, deux en-têtes Cache-Control concurrents sont émis (expires 1y; en produit un, l'add_header un second) — comportement indéfini côté intermédiaires.

👉 Corrigé dans le dépôt : voir §8.

admin/deploy/nginx-neogtb-laravel.conf Moyen

Le fichier versionné date du 7 avril 2026 et n'a jamais été resynchronisé, alors que la production a été durcie depuis. Écarts constatés :

Le risque n'est pas théorique : la procédure de déploiement du projet resynchronise la configuration nginx manuellement. Une configuration versionnée fausse est plus dangereuse qu'une configuration absente.

5.3 — Trois constats issus du second audit, revérifiés ici

Un second rapport a été produit en parallèle (docs/audit-securite-neogtb-2026-08-15.md). Ses relevés ont été recontrôlés un par un : versions exactes des dépendances, DNS, DKIM sur 12 sélecteurs, CVE. Ils sont exacts. Trois de ses constats manquaient au présent rapport et sont repris ici, avec leur vérification propre.

CORS ouvert sur les routes /api/ Faible

$ curl -sI -H "Origin: https://evil.example" https://neogtb.fr/api/user | grep -iE "^(HTTP|access-control)"
HTTP/2 404
access-control-allow-origin: *

Confirmé, y compris avec une origine hostile — et la v1 affirmait exactement l'inverse (« Pas de CORS ouvert, aucun header Access-Control renvoyé »). Aucune donnée n'est exposée par ces routes aujourd'hui, mais la valeur par défaut de config/cors.php mérite d'être resserrée avant qu'une route /api/ utile n'apparaisse.

/adminer.php révèle le sous-domaine d'administration Faible

$ curl -s -o /dev/null -w "%{http_code} %{redirect_url}" https://neogtb.fr/adminer.php
301 https://admin.neogtb.fr/adminer.php

Aucun outil de base de données n'est exposé (la cible répond 404), mais un scan automatisé de chemins usuels obtient gratuitement l'adresse du back-office. Cette redirection ne figure pas dans la configuration versionnée : troisième manifestation de la dérive du §5.2.

CVE-2026-42945 (« NGINX Rift ») — exposition improbable, motif à corriger Moyen

Faille réelle, divulguée le 18 mai 2026, corrigée en nginx 1.30.1 / 1.31.0 ; toutes les versions de 1.0.0 à 1.30.0 sont concernées. Le second rapport conclut à juste titre que l'exposition est improbable, mais son motif est incomplet : il écarte le risque au motif qu'« aucune directive rewrite » n'est utilisée, alors que if et set déclenchent la même faille — et la configuration en contient. La condition exacte est la conjonction d'une capture PCRE non nommée ($1, $2…) et d'un ? dans la chaîne de remplacement. Aucun des if de cette configuration ne réunit les deux (aucune capture n'y est utilisée), donc la conclusion tient — sur un motif vérifiable.

Le contrôle à faire n'est donc pas « cherchons les rewrite » mais : grep -nE '(rewrite|if|set)\b.*\$[0-9]' sur la configuration déployée, puis vérifier la présence d'un ? dans le remplacement. Version de nginx en production toujours non relevée : à confirmer par nginx -v sur le VPS.

7. Ce qui n'a pas été mesuré

Par honnêteté d'audit, voici ce sur quoi aucune note n'est décernée, faute de mesure — là où la v1 attribuait des A et des B sans instrument.

  • TLS / SSL — la v1 annonce « A+ », « TLS 1.2+ », « X25519 ». Aucune de ces valeurs n'a été reproduite ici : la suite négociée par un client donné ne dit rien des suites acceptées. Verdict à obtenir de SSL Labs, pas d'un curl.
  • Conformité RGPD — la v1 note « A ». Les pages existent bien (/mentions-legales, /politique-de-confidentialite, /mes-droits-rgpd, /cookies, registre dans docs/REGISTRE_TRAITEMENTS_RGPD.md), mais leur contenu n'a pas été relu. L'existence d'une page n'est pas sa conformité.
  • Robustesse de l'authentification admin — aucune limitation de tentatives n'a été trouvée sur la connexion Filament, mais le point n'a pas pu être testé : la page renvoie 500. À reprendre une fois le §3 réglé.
  • Indexation effective de admin.neogtb.fr — la duplication est prouvée, son indexation réelle demande la Search Console.
  • Dépendances — aucun composer audit ni npm audit n'a été exécuté. À intégrer à la CI.
  • Test d'intrusion applicatif — hors périmètre. Cet audit porte sur la configuration, pas sur la logique métier (droits d'accès Filament, IDOR, injections).

Conclusion

Le travail de fond est bon. CSP par nonce, throttling systématique sur les écritures, HSTS preload, cookies corrects, robots.txt pensé jusqu'aux crawlers génératifs, security.txt publié : c'est nettement au-dessus de ce qu'on rencontre sur un site de cette taille, et rien de tout cela n'est accidentel.

Les défauts réels sont ailleurs que là où un scanner regarde. Les trois problèmes sérieux — DMARC annulé par un doublon, back-office en 500, site public dupliqué sur le sous-domaine admin — ont un point commun : aucun ne se voit dans une liste d'en-têtes HTTP. Ils demandaient de lire le code, d'interroger le DNS et d'ouvrir réellement les URL. La v1 ne l'a pas fait, et a produit à la place une liste d'ajouts d'en-têtes dont deux étaient inopérants et quatre déjà en place.

La leçon opérationnelle tient en une ligne : un audit qui ne cite pas sa preuve n'est pas un audit. Chaque ligne de ce document est rattachée à une commande reproductible ou à une référence fichier:ligne — y compris les rubriques où la réponse est « non mesuré ».
